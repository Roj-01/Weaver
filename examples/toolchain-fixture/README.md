# Weaver toolchain fixture

A server-side fixture mod that exercises the Gradle toolchain end to end:

- a Maven-style dependency with a Gradle/Maven version range
  (`fixture-lib:[1.0,2.0)`); the generated descriptor uses the loader-compatible
  `>=1.0` constraint;
- a transitive dependency declared in the library POM
  (`fixture-lib` -> `fixture-transitive`);
- an optional dependency (`fixture-optional`) that is resolved but never
  embedded;
- a nested subproject built with `weaverBuild` and embedded as a jar-in-jar
  payload (`fixture-nested`);
- deterministic `META-INF/weaver/jij.json` plus
  `META-INF/weaver/jars/*.jar` entries;
- loader discovery through `net.weaver.core.ModLoader` and
  `net.weaver.core.jij.JijScanner`;
- a real dedicated-server run through `tools/launcher/launch.ps1`.

## Layout

```text
examples/toolchain-fixture/
  build.gradle.kts                 main fixture mod
  settings.gradle.kts              includes :nested
  nested/                          nested jar-in-jar mod subproject
  maven-lib/                       publishes fixture/repo
    fixture-transitive/
    fixture-lib/                   api(project(":fixture-transitive"))
    fixture-optional/              resolved as weaverOptional, never embedded
  loader/LoaderProof.java          loader discovery and JijScanner proof
  build.ps1                        build and jar-layout verification
  loader-proof.ps1                 compiles and runs LoaderProof
  proof.ps1                        real dedicated-server proof
```

The local Maven repository is `examples/toolchain-fixture/repo`. It is
generated by `maven-lib`; it is not checked in.

## Commands

Run from `examples\toolchain-fixture` with JDK 26:

```powershell
.\build.ps1              # build api/agent, publish repo, build mod, verify jij, run loader proof
.\build.ps1 -SkipRun     # stop after the jar-layout verification
.\loader-proof.ps1       # re-run only the loader/JijScanner proof
.\proof.ps1              # run the real dedicated server proof on port 25567
```

`build.ps1` runs these steps and stops on the first failure:

1. `..\..\gradlew.bat -p ..\.. :api:jar :core:agentJar`
2. `..\..\gradlew.bat -p maven-lib publish` (writes `fixture/repo` and its
   `maven-metadata.xml` version listings so the `[1.0,2.0)` range resolves)
3. `..\..\gradlew.bat weaverResolveMods weaverBuild weaverStage weaverExportJij`
   (stages the main jar and extracts the nested jars into `build/weaver/mods`)
4. `jar tf` on `build/libs/*.jar`: requires `META-INF/weaver/jij.json` and
   `META-INF/weaver/jars/fixture-lib-1.0.0.jar`,
   `fixture-transitive-1.0.0.jar`, and `fixture-nested-1.0.0.jar`; fails if any
   `fixture-optional` entry is present
5. `loader-proof.ps1` unless `-SkipRun` was passed

The path properties default to the repository layout
(`../../api`, `../../core`, `../../work`, `../../tools/launcher`). Set
`WEAVER_API_JAR`, `WEAVER_GAME_API_JAR`, `WEAVER_AGENT_JAR`,
`WEAVER_LAUNCHER`, `WEAVER_GAME_DIR`, or `WEAVER_SERVER_DIR` to override them.

`proof.ps1` requires `work/server-26.3` (or `WEAVER_SERVER_DIR`) and the run
mods directory produced by `build.ps1`.

## What the scripts assert

`build.ps1`:

- `weaverResolveMods` resolves the range dependency and its POM transitive
  dependency, and resolves the optional dependency separately;
- the built mod jar embeds exactly the three expected nested jars and no
  optional jar.

`loader-proof.ps1` / `loader/LoaderProof.java`:

- copies the fixture jar and the extracted `jij-*.jar` files from
  `build/weaver/mods` into a temporary mods directory;
- `ModLoader.discover(temp, "server", ...)` accepts `toolchain-fixture`,
  `fixture-nested`, `fixture-lib`, and `fixture-transitive`, and rejects
  `fixture-optional`;
- `JijScanner.scan(mainJar)` returns three nested jars with the expected ids,
  versions, and entry names, in a deterministic order across repeated scans;
- prints `TOOLCHAINFIXTURE LOADER ok=true mods=<n> nested=<n>`.

`proof.ps1`:

- launches the real dedicated server with the fixture in the mods directory;
- waits for `TOOLCHAINFIXTURE RESULT ok=true side=server`;
- prints the `TOOLCHAINFIXTURE main`, `nested`, and `RESULT` markers.

The main mod reflectively reads `Library.value()`, `Transitive.value()`, and
`NestedPayload.value()` during `onInitialize` and reports:

```text
TOOLCHAINFIXTURE main ok=true lib=fixture-lib-1.0.0 transitive=fixture-transitive-1.0.0 nested=nested-1.0.0
```

## JIJ discovery

`LoaderAgent` discovers jars embedded inside another mod jar by itself: it
calls `ModLoader.discover(modsDir, side, log, policies, <dataDir>/jij)`, which
extracts each parent's nested jars into `<dataDir>/jij/<parent>/` and loads them
as ordinary mods. A broken nested entry is logged as `MOD JIJ FAILED` and does
not block the parent. `ModLoaderNestedJarTest` covers this path end to end.

This fixture predates that wiring and still uses the Gradle-side bridge:

- `weaverBuild` embeds the nested jars under `META-INF/weaver/jars/` and writes
  `META-INF/weaver/jij.json`;
- `weaverExportJij` extracts them into `build/weaver/mods` as
  `jij-<index>-<id>-<version>.jar`;
- `LoaderProof` copies the main jar and those extracted jars into one mods
  directory so `ModLoader.discover` sees them as ordinary mod jars.

This proves resolution, embedding, extraction, and loader discovery. Because the
loader now extracts nested jars itself, `exportJijForRun` can be set to `false`;
it stays enabled here so the fixture keeps proving the Gradle export path. A
live in-game boot of a jar-in-jar mod has not been recorded yet.

## Version range syntax

The Gradle dependency uses the Maven range `[1.0,2.0)`, so dependency
resolution exercises Gradle/Maven range handling. The generated
`weaver.mod.json` uses the loader-compatible `>=1.0` constraint because
`net.weaver.core.VersionRange` understands comparator constraints such as
`>=1.0`, `<2.0`, `~1.2`, and `^1`, but not Maven bracket ranges. Keep the two
syntaxes separate: Gradle coordinates resolve artifacts, descriptor metadata
is validated by the loader.
